# CI/CD 学习笔记

> 目标：学完能独立给任何 C# 项目接入流水线，面试对答如流
> 项目：TodoApi（ASP.NET Core Minimal API + xUnit）· 平台：GitHub Actions

## Phase 0：环境与概念

### 关键概念

- CI（持续集成）：每次 push 自动构建 + 测试，尽早暴露问题
- CD（持续交付 / 持续部署）：交付 = 制品随时**可**上线（上线需人工点按钮）；部署 = 连上线都全自动
- 为什么需要 CI：人为失误、环境不一致、集成太晚（三大痛点）
- Docker 是 C/S 架构：敲的命令只是客户端，真正干活的是 daemon（引擎）。Docker Desktop 的引擎在 Windows 侧，WSL 里通过"集成"只放一个客户端命令

### 环境相关的坑

- `~/.profile`（登录 shell 读，放环境变量最正统）vs `~/.bashrc`（交互 shell 读，开头有非交互守卫，后面追加的内容非交互 shell 看不到）
- 进程的环境变量在启动那一刻"定格"，改完配置必须**重启进程**才生效（VS Code 找不到 SDK 的教训）
- .NET 依赖 ICU（国际化库）：脚本安装不解析系统依赖（要自己装 libicu），apt 安装会自动带上——这就是依赖解析的区别

## Phase 1：手动构建四部曲（CI 要自动化的就是它们）

### 命令

| 命令 | 作用 |
| --- | --- |
| `dotnet restore` | 还原 NuGet 包到 `~/.nuget/packages`，解析结果写入 `obj/project.assets.json` |
| `dotnet build --no-restore` | 编译成 IL 输出到 `bin/`。默认 Debug（不优化、带调试符号）；发布用 Release |
| `dotnet test --no-build` | 跑测试。改过代码必须重新编译，否则测的是**旧二进制**（CI 里 restore → build → test 的顺序就是为此） |
| `dotnet publish -c Release -o publish` | 产出部署三件套：`TodoApi.dll`（IL）+ `deps.json`（依赖清单）+ `runtimeconfig.json`（运行时配置） |

### 关键概念

- 退出码：**0 = 成功，非 0 = 失败**（不止 1：130 = Ctrl+C 中断，139 = 段错误）。用 `echo $?` 查看
- CI 红绿灯：平台并不"看懂"测试，只检查命令退出码，非 0 → 红灯 → 中止后续步骤
- 单元测试 vs 集成测试：
  - 单元：测最小单元，不依赖外部设施，毫秒级，量大面广（直接 `new TodoService()` 测）
  - 集成：多组件组装后测，覆盖核心流程，接受较慢（C# 用 `WebApplicationFactory` 可在内存中起整个应用）
- 测试金字塔：大量单元测试保逻辑 + 适量集成测试保组装 + 少量 E2E 保核心业务流

## 面试速答（Phase 0-1）

- Q：为什么要做 CI？ → 手工构建发布有人为失误、各人环境不一致、集成太晚问题难定位；自动化后每次提交都被验证
- Q：CI 怎么知道测试失败了？ → 看命令退出码，非 0 即失败，红灯中止流水线
- Q：你们项目的测试策略？ → 测试金字塔：大量单元测试保证逻辑，少量集成测试验证组装，E2E 只覆盖核心流程
- Q：Debug 和 Release 的区别？ → Debug 不做优化、带调试符号便于开发调试；Release 做优化，用于发布
- Q：dotnet publish 产出什么？ → IL 程序集 + 依赖清单（deps.json）+ 运行时配置（runtimeconfig.json）
- Q：改了环境变量为什么正在运行的程序不受影响？ → 进程环境变量在启动时定格，必须重启进程
- Q：docker 是客户端还是服务端？ → C/S 架构，CLI 是客户端，daemon 是干活的服务端，两者可分离甚至远程

## Phase 2：Git 与 GitHub 协作流

### 关键概念

- 本地仓库：git仓库是一个分布式仓库，github可以理解成是一个远程的备份同步仓库，然后本地电脑上也有一个完整的版本控制仓库，正常工作都是在本地电脑上进行版本管理，然后会把本地仓库变更同步到远程仓库。一是为了仓库安全，启动备份作用，二是通过远程仓库作为媒介，可以实现团队的协作。
- 远程仓库：服务器上的仓库，github这个就是
- push本地仓库：把本地仓库的变更提交历史同步到github，github ci触发器检测到push事件后，触发CI流程

### 面试速答

- 为什么要用功能分支？ → main主分支永远保持可发布状态，修改一半的或者未验证的代码呆在功能开发分支上，不影响主功能，也不影响别人。测试验证审核过的代码再合并到主分支。
- 为什么用PR而不是直接推main? → 1、强制代码审查 2，CI检查挂在PR上  红了就合不进主分支  3，讨论和决策留痕，以后可以回顾当时为什么添加这个功能
- 为什么要 Conventional Commits（feat:/fix: 前缀）？ 提交信息结构化后，机器可以自动生成 changelog、自动推断版本号（feat → 升次版本，fix → 升修订版本）——Phase 5 自动化发布时你会亲手受益。
- 使用Squash合并有什么问题？ 假如是合并到main分支，会把多次提交合并成一个新的在main分支上的提交。所以问题是丢失原始的详细的提交历史记录。但从软件过工程来看，▎ 分支内的提交过程是"工作噪音"，PR 才是有意义的交付单元。 main 的历史应该回答"何时交付了什么"，而不是复述你开发时的挣扎过程（"fix typo"、"再修一次"、"终于好了"）。

## Phase 3：第一条流水线

### 关键概念

#### github action 相关概念

- workflow：.github/workflows目录下面一个.yml文件就代表一个流水线，完成一个特定任务，比如代码校验、CI持续集成等
- 触发器(on)：定义出现什么事件时，会启动这条流水线，比如push到mai,比如如何的pr请求
- job：流水线中定义的一项任务，或者叫一个工作岗位，完成一个特定任务。分配一台`runner`(全新的虚拟机，比如ubuntu)来执行这个job
- runner：运行job的虚拟机，用完即焚，下次运行时，又会创建一台新的runner虚拟机
- steps：按需执行的小步骤，两种写法：
  - `uses:` —— 直接调用别人写好的"积木（action）"，例如官方的actions：拉代码，装sdk等，可以是`with`传递参数
  - `run:` —— 直接运行shell命令

### 面试速答

- runner 是一次性虚拟机，每次 push 都要重新下载 NuGet 包。现在只有几个包无所谓，真实项目几百个包时这就是浪费的生命。

  GitHub 给每个仓库提供一个缓存仓库（上限 10GB，按 LRU 淘汰），用 key 存取目录  

- ${{ }}表达式语法

  流水线里的模板语言，运行时求值。runner.os 取当前系统，hashFiles() 计算匹配文件的哈希——csproj 一变，key 就变

- 缓存不可变（immutable）

  同一个key只能 **写入一次**，永不覆盖。所以 key 里 放哈希：依赖变了  → 新 key → 新缓存；依赖没变 → 命中旧缓。
  
  如果key写死成nuget，依赖更新后你将永远拿到的是旧缓存！！！这是最大的坑！！！

- restore-keys兜底

  如果精确 key 没有命中时，退而求其次找前缀匹配的最近缓存恢复，然后 `dotnet restore` 只下载缺的那几个包
  - 精确 key 中包含所有 .csproj 的哈希；只要改动其中任意一个，哈希就会变化，导致精确匹配失败。
  - 此时会按 nuget-Linux- 这个前缀查找，取最近一次 Linux runner 保存的 NuGet 缓存并恢复它
  
  实际运行效果：
  - 首次运行：精确 key 和前缀都未命中 → 从零执行 dotnet restore → 任务结束时按 key 保存缓存。
  - 未改 csproj：精确 key 命中 → 直接恢复缓存，速度最快。
  - 改了 csproj：精确 key 未命中 → 通过 restore-keys 恢复旧缓存（部分命中）→ 只下载新增或变更的包 → 结束时按新 key 再存一份。

## Phase4：质量门禁，把标准变成机制

### 面试速答

- 为什么测试时增加覆盖率检查，需要移除--no-build？

  coverlet 的原理是在编译时给程序集"插桩"（注入统计代码），--no-build 跳过编译 = 没插桩 =没有数据。

- asp.net web 应用的集成测试原理

  `WebApplicationFactory<Program>` 会在内存里启动整个应用，不占端口，不起真实网络，但路由，模型绑定，json序列化全部真实执行。

- 为了集成测试，为什么要在 Program.cs 末尾追加一行：`public partial class Program { }`

  因为 top-level statements 会生成一个internal的program类，测试项目就看不见它。public partial把它公开。Minimal API + 集成测试的标准开场咒语
- 如何保证软件测试的代码覆盖率？

  使用阈值防退化。覆盖率衡量的是"这行代码有没有被执行过"，而不是验证这个代码逻辑对不对，即使把所有的Assert删除，覆盖率照样可以是100%。所以覆盖率100%≠无bug

- github如何对main分支保护，必须通过状态检查的代码才能合并？

  设置runset,设置必须通过pr，必须过状态检查，必须是最新，管理员不豁免

## Phase5：制品与版本发布

### 关键概念

- 制品(Artifact)：构建产物的存档，挂在运行记录页，可下载，给机器和人存证用
- 发布（Release）：面向人的版本发布页——版本号，变更说明、附件下载。给用户看
- 语义化版本：MAJOR-MINOR-PATCH = 破坏性变更-新功能-bug修复。0.x.x表示开发期不稳定版本，1.0.0是可以商用的正式版本
- ${{ github.sha }}：github 上下文对象——流水线运行时的“自我描述”，.sha 是触发本次运行的提交哈希、.ref_name 是分支或tag名、.token后面会用到。制品名带 sha = 每次运行的产物可区分。

## Phase6: Docker化

### 关键概念

- DockerFile: 镜像的配方（声明式构建脚本）
- 镜像：按配方构建出的分层快照
- Registry: 镜像的仓库
- GHCR: GitHub Container Registry,github的镜像仓库。

### 面试速答

- .dockerignore的作用
  
  有双重作用：
  - COPY的上下文瘦身，忽略ignore中的文件夹及文件，构建更块
  - 防止本地bin obj混进镜像，本地产物污染会导致“镜像构建结果随机器不同而变”，缓存也会失效

### 多阶段构建

- 精装房类比：微软在 Docker Hub 卖精装房（aspnet:10.0 镜像），Ubuntu 地板 + .NET 水电 + 系统依赖全装好，我拎包入住，行李只有 152kB（编译好的应用）
- 两阶段结构：
  - 阶段1 build：用 sdk 镜像（含编译工具链，700MB+），负责 restore + publish
  - 阶段2 final：用 aspnet 镜像（只有运行时），通过 `COPY --from=build` 只借走成果物
- 意义：编译用厨房，交付只上菜——SDK 工具链不进最终镜像，700MB → 120MB 级

### 镜像结构（docker history 解读）

- `docker history 镜像名` = 从最新层（上）到最老层（下）的装修清单
- 我的层（刚构建）：WORKDIR（建目录）/ COPY 152kB（我的应用本体）/ EXPOSE、ENTRYPOINT（0B 纸条）
- 微软的层（4天前，基座镜像，全网共享只读）：
  - Ubuntu 系统 87.6MB
  - apt-get 系统库 45.8MB（含 ICU——Phase 0 手动装过的那个，镜像里已装好）
  - .NET / ASP.NET 运行时 83.2 + 27.4MB
- 0B 层 = 纯元数据（ENV / EXPOSE / ENTRYPOINT 只是"纸条"，不占空间）
- 基座里有 `ENV ASPNETCORE_HTTP_PORTS=8080` → 容器默认监听 8080 的原因
- `ENV APP_UID=1654` → .NET 官方镜像默认非 root 用户运行（容器安全基本功）

### 分层缓存（Docker 的灵魂）

- 镜像 = 一层层叠起来的快照，Dockerfile 每条指令 ≈ 一层
- 缓存按**依赖图（DAG）**匹配，不是整个文件从上到下一条线：
  - 圈内传染：同一 FROM 阶段内，某层失效 → 它下面的层全部重做
  - 圈间靠水管：阶段之间通过 `COPY --from` 传数据，只有数据流到的层才会重建（改源码后 final 圈的 WORKDIR 命中缓存、COPY --from 重建）
  - 基座共享：FROM 的基础镜像层不可变，永远复用
- Dockerfile 排序哲学：变得少的放前面（csproj → restore），变得多的放后面（源码 → publish）
- 和 CI 里 NuGet 缓存 key 用 csproj 哈希是同一个思想：变则换，不变则复用

### 面试速答（续）

- 为什么用多阶段构建？ → 编译用 SDK 镜像，交付只拷成果物进 aspnet 运行时镜像，工具链不进最终镜像，700MB 降到 120MB 级；我的应用层只有 152kB，其余 ~250MB 是共享基座
- Docker 构建缓存按什么匹配？ → 按依赖图：每层的 key = 指令 + 输入内容 + 圈内祖先链；失效沿圈内向下传染、沿 COPY --from 跨圈传播，基础镜像层永远复用
- 改一行代码，为什么镜像重建还是很快？ → 源码变化只污染 build 圈下半段和 final 圈的 COPY --from 一层，基座、restore、final 前置层全部命中缓存
- EXPOSE 8080 是什么作用？ → 只是声明/文档（0B 元数据），真正映射端口靠 docker run 的 -p 参数

### 容器运行常用命令

- `docker build -t todo-api:local .` 构建并打标签
- `docker run --rm -d -p 8080:8080 --name todo-local todo-api:local`
  - -d 后台运行 / --rm 停止后自动清理 / -p 宿主机端口:容器端口 / --name 容器命名
- `docker logs <容器名>` 看容器标准输出；`docker stop <容器名>` 停止
- `docker images` 看镜像大小；`docker history <镜像>` 看分层结构

### CI构建镜像 + 推送 GHCR

- 为什么在 CI 里构建镜像：

  - 一致性：同一份 Dockerfile 在同一环境构建，杜绝“本地镜像能跑”；
  - 自动化：测试绿了自动产出镜像，人手不碰；
  - 为 CD 铺路：Phase 7 部署时机器从 registry 拉镜像，而不是拷文件。

## Phase7: CD部署：流水线第一次改变真实世界

到目前为止，流水线这样的都是“验证与产出”（测试，构建，推送）。CD部署是流水线动手改造真实环境——在用户机器上跑起你自己的服务。

### 关键概念

- 云端runner: github的机器
- self-hosted runner: 是你自己注册给仓库的机器，github 流水线把job派发给它执行。

### 云端部署 —— 让全世界访问你的 API

- <https://render.com> → Get Started → 用 GitHub 账号登录（这就是为什么镜像在 6.5 改成了 Public）
- Dashboard → New + → Web Service → 选 "Deploy an existing image from a registry"（部署现成镜像，不是连 Git 仓库——我们的交付物是 GHCR 里的镜像）
- 填写：

  | 项 | 值 |
  | --- | --- |
  | Image URL | `ghcr.io/liuww06/todo-api:latest` |
  | Name | todo-api |
  | Region | Singapore（离得最近） |
  | Instance Type | Free |
  | Health Check Path | `/health` |

- 关键一步——环境变量区添加：
  
  ASPNETCORE_HTTP_PORTS = 10000

- Create Web Service → 等它拉镜像、启动 → 拿到形如 <https://todo-api-xxxx.onrender.com> 的地址

### 面试速答

- 持续交付和持续部署的分水岭是什么？

  添加审批，执行部署前需要用户审批，就是持续交付，如果没有审批，自动部署，就是持续部署。看风险偏好，然后决定是持续交付流程，还是持续部署流程

- 幂等是什么，为什么部署要幂等？

  同一个操作重复执行，结果还能保持一致，这个就是幂等。为什么部署如果有事故，就可能需要多次运行部署，如果不是幂等的部署脚本，你就不敢重复跑，导致事故恢复慢

### 实战故障复盘（7b.2 全链路大考）

#### 故障一：容器名漂移——`|| true` 吞掉了线索

- 现象：第二次部署时，"启动新容器"步骤报错"本地已有一个 running 状态的容器"，手动删掉重跑 job 才恢复
- 定位：对比两个步骤发现——`docker rm -f todo-api` 删的是 **todo-api**，`docker run --name todo-api-prod` 启动的是 **todo-api-prod**，两个名字对不上
- 根因：清理步骤删错对象（todo-api 根本不存在，报"no such container"被 `|| true` 吞掉），旧容器 todo-api-prod 从未被删 → docker run 撞名
- 为什么第一次部署成功：当时机器上还没有 todo-api-prod，无冲突——bug 埋下但休眠，到第二次部署才爆
- 修复：清理与创建的名字必须一致；进阶做法是把容器名收敛成 job 级环境变量 `env: CONTAINER_NAME`，名字只写一处永不漂移（DRY）
- 沉淀原则：
  - `|| true` 做幂等的代价：它把"本来不存在"（预期）和"删错了对象"（bug）一起吞掉，让 bug 休眠到更晚才暴露
  - 同一个名字出现在多处（清理/创建/日志/健康检查），就必须用变量收敛

#### 故障二：Render 静止——镜像推了，云端不更新

- 现象：CI 全绿、新镜像已推 GHCR，但 `https://todo-api-2flo.onrender.com/health` 返回的还是旧版本
- 定位：排查"**谁负责通知 Render 更新**"——Render 页面找不到 Auto-Deploy 配置项，流水线里也没有 deploy-cloud job → 结论：**没有任何东西通知它**，镜像静静躺在 GHCR，Render 还跑着创建时拉的旧 digest
- 修复（两步）：
  1. 立刻验证链路：Render 页面 → Manual Deploy → Deploy latest reference（强制拉一次 latest）
  2. 自动化：Render 生成 Deploy Hook URL → 存进 GitHub Secrets（`RENDER_DEPLOY_HOOK`）→ ci.yml 加 deploy-cloud job，在流水线里 curl 钩子主动触发部署
- 沉淀原则：
  - 部署触发链必须显式闭环：平台不会"自己知道"有新镜像——要么轮询（平台定期查 registry）、要么钩子（流水线主动通知）、要么手动，三选一，不能空缺
  - Deploy Hook URL = 部署钥匙，必须走 Secrets（`${{ secrets.XXX }}`），明文进 YAML 或仓库 = 泄漏
  - 排障思路："不工作"先问"这个环节应该由谁触发"，从触发链找断点

## Phase8 毕业战：面试冲刺

1. CI 和 CD 分别解决什么问题？持续交付和持续部署差在哪？
   - 我的回答：

     CI解决的是对代码的各类检查和测试，通过的代码才可以进入代码库。CD解决的时，如果把合并到代码库的新软件快速部署到生成环境。
   - 补充：

     CI：频繁小步集成，每次提交都被验证，问题在合并前保留，这是CI的灵魂，检查、单元测试只是试下这个目标的手段。

2. 画/说一遍你们项目从“开发者提交”到“用户可用”的完整链路。
   - 我的回答：

     开发者拉取主分支最新记录，切换到功能分支修改代码，提交，推送到远程仓库，然后创建pr,管理员接收pr，触发ci流程，检查测试一切顺利后，自动触发cd
   - 补充：
     1. pr上的CI是门禁 —— 红灯物理上合不进（分支保护），不是管理员看一眼
     2. 合并到 main 后push事件再次触发CI——构建镜像推 GHCR （lastest + sha  双标签，既方便拉取最新镜像，也方便版本回滚）
     3. 审批环节 + 双端并行部署 —— production environment 审批 -> 本机 self-hosted || render 钩子 -> 监控检查

     完整版（背这个）：
     > “PR 触发门禁 CI（测试+覆盖率+格式）→ 审查合并（squash）→ main 的 push 触发主 CI：测试+构建镜像推 GHCR →  production 环境审批 → 本机 self-hosted runner 和 Render 钩子并行部署 → 各自健康检查。”

   流水线靠命令执行的返回码，非0代表执行失败，可以靠这个截断后续job和step

4. 缓存 key 为什么要放哈希？写死一个固定 key 会怎样？
   - 我的回答：

     使用hash的好处是，代码或者特定文件有变化，hash就改变了，自动让key失效，如果写死key，那缓存永远是旧的有效，即使修改了依赖或者代码，也只能依赖旧的缓存
   - 补充：

     你说“代码有变化 hash 就改变”——注意：我们的 key 哈希的是 csproj（依赖声明），不是源码！这是刻意设计：
     - 依赖变 → key 变 → 新缓存 ✅
     - 只有代码变、依赖没变 → key 不变 → 缓存命中（这正是想要的！如果 key 跟着代码变，缓存永远不命中，等于没做）
     - 再补一句 restore-keys 兜底（部分命中+增量下载）就满分了。

5. 你们的 Dockerfile 为什么要多阶段？最终镜像里都有什么？
   - 我的回答：

     多阶段的好处是构建阶段的sdk和中间产物不进行最终镜像。最终镜像里面是运行时和构建的程序产物
   - 补充：

     核心对（SDK 和中间产物不进最终镜像）。补两个数字一句机制，说服力翻倍：
     - 量化：“SDK 阶段 700MB+，最终镜像 120MB 级，应用层本身只有 152kB”
     - 机制：“COPY --from=build 只把 publish 产物带进 runtime 基座”
     - 加分：“工具链不进生产镜像也减小了攻击面——容器里没有编译器，漏洞面就更小”

6. 为什么 Dockerfile 里先拷 csproj 还原依赖、再拷源码？这和哪个缓存原理同源？
   - 我的回答：

     因为csproj一般比较稳定，这样构建的缓存可以重复使用，不用每次都需要完整还原依赖。
   - 补充：

     “csproj 稳定 → 缓存复用” ✓，但机制和类比都没展开：
     - 机制句：“分层缓存失效会向下传染——把稳定的放前面，源码变化只污染下半段，restore 层永远幸免”
     - 问题后半句“与哪个原理同源”没答：NuGet 缓存 key 用 csproj 哈希——同一个思想：依赖声明变则换，不变则复用。面试官问“和什么同源”就是在等你这句。

7. squash merge 有什么坑？你们团队怎么规避？
   - 我的回答：

     squash merge会创建一个新的合并提交，会掩盖了原始提交，导致pr可以重复发起
   - 补充：

     “新提交 + 原始提交不在 main 血缘 → 同分支可重复开 PR”——完全正确，还是你亲手踩的。补全“规避”半题：
     > 合并后立即删分支（每个功能一个全新短命分支）；若必须继续用旧分支，先 rebase main。加分句：“PR 页面永久保留原始提交，信息没灭，只是入口从 main 移到了 PR。”

8. 部署脚本怎么做到幂等？你踩过什么相关的坑？
   - 我的回答：

     要保多次执行都能正常返回结果，可以使用|true这个逻辑来上线，但这个会导致完成错误的指令也逃逸了，比如我删除一个一个容器，即使名称写错了，也让执行返回正常，导致后续流程有问题
   - 补充：

     不仅答了定义，还主动交代了 || true 的代价和自己的真实事故（名字写错也逃逸 → 后续流程爆雷）。“定义 + 边界 + 亲历案例”三连，这就是面试官记住你的方式。唯一点缀：结尾补一句修法——“我们后来把容器名收敛成环境变量，保证清理和创建永远同名”。

9. 生产环境出问题要回滚，你们怎么做？（提示：想想你的双标签）
   - 我的回答：

     可以使用指定标签的docker Image进行恢复
   - 补充：
     “用指定标签的镜像恢复” ✓。展开成三句：

10. GITHUB_TOKEN 是什么？权限上你们遵守什么原则？
    - 我的学习：

      背下这段：
      >"GITHUB_TOKEN 是每次流水线运行自动发放的临时身份，代表‘这次运行’而不是某个用户。默认最小权限（只读），哪个 job 需要什么能力，就在那个 job 的 permissions 显式声明——我们发布 Release 用 contents: write，推镜像用 packages: write，都是 job 级声明，用完即废。"

      三个辨析（被追问时用）
      - vs PAT（Personal Access Token）：PAT 是长期有效的用户身份、手动管理；GITHUB_TOKEN 一次性、运行级
      - vs Secrets：secrets 是你自己存的钥匙（如 Render 钩子）；GITHUB_TOKEN 平台自动注入 ${{ github.token }}
      - 原则一句话：“最小权限 + 按需按 job 提权”

11. 你们的分支保护怎么配的？如果流水线里把 job 改名，会发生什么？
    - 我的回答：

     我们的main分支配置禁止直接push,必须统pr合并。如果流水线中修改job名称，应该没什么影响，历史记录还是旧名字，但新流程使用新名字

    - 补充：

      🔴 后半题踩中了我埋的雷
      >“job 改名没什么影响”是错的——这正是 Phase 4 讲的经典生产事故：分支保护里 required status check 匹配的是 job 名。改名后 ruleset 永远等旧名字 → PR 卡死在 Expected — Waiting for status report → 全员合不了并。修法：改 job 名必须同步更新分支保护里的必需检查。

14. 你们的测试怎么分层？集成测试用什么写的、原理是什么？
    - 我的回答：

     单个小的功能，对外没有依赖，频繁要验证的测试的放在单元测试，核心业务流程，需要依赖支撑的，运行耗时放在集成测试。web api应用使用WebApplicationFactory写，原理是模拟一个hettpclient，实现对api的调用

    - 补充：

      分层标准答得好 ✓。原理句要倒过来背：WAF 在内存中启动真实应用（路由/绑定/管道全真），再给你一个 HttpClient 打这条内存管道——不占端口、不出真实网络。是“服务器被搬进测试进程”，不是“模拟 HttpClient"。

    - 补充：

20. 为什么要求 main 永远可发布？开发到一半的功能怎么合进 main？
    - 我的回答：

    我们的工程规范是要求main是稳定版本，我们通过ci流水线门禁保证审查通过的代码进行分支，使用永远可发布。我们禁止开发到一半的功能合并进main分支

    - 补充：
      前半 ✓。“禁止半成品合并”在真实世界撑不住——正确姿势是功能开关（Feature Flag）：代码进 main 但功能对用户关闭（if (featureEnabled) 分支），实现“主干永远可发布”而不用憋大招；辅以小步垂直切片（每次合并一个可用的小功能）。
